# AGENTS.md

Short operational index for contributors and agents. Follow the linked documents for procedure and rationale.

## Start here

- [README](README.md): what the project is and how to run it.
- [CONTRIBUTING](CONTRIBUTING.md): the dev/main branch workflow.
- Organisation guide: commit, branch, pull request, issue and agent rules. After `scripts/agents/setup.sh`, read the local copy in `.agents/org-contributing.md` instead of fetching it. When a rule here conflicts with the organisation guide, this file wins.

## Setup

Run `scripts/agents/setup.sh` once per clone. It creates the tool-specific files (for example `CLAUDE.md`) and the local organisation guide, and lists them in `.git/info/exclude`. Do not commit tool-specific files.

Use the Node version in `.nvmrc` and the pnpm version in `packageManager`, then run `pnpm install`.

## Layout

- `apps/`: `api`, `web`, `admin`, `idle`, `ops`.
- `packages/`: `api-contract`, `ui`, `config`.
- `docs/`: documentation and decision records.
- `infra/`: infrastructure.

## Mandatory for every task

- Do only what the issue or request asks. Record follow-up work as a new issue.
- Never read `.env` files or production tokens. Use `.env.example` to learn which variables exist.
- Never commit secrets, personal data or `.env` files.
- Branch from an up-to-date `dev` as `<type>/<short-kebab-case-description>` using Conventional Branch types (`feat/`, `fix/`, `docs/`, `chore/`, and so on). Never work directly on `main` or `dev`.
- Use Conventional Commits with a one-line header under 72 characters. Write no body, no footer and no AI co-author or "generated by" lines. Split unrelated work into separate commits.
- Commit and push only when asked. Never force-push or rewrite shared history.
- Open the pull request into `dev`, never `main`. A reviewed `dev` to `main` promotion pull request ships a release. Never merge a pull request or open a promotion pull request unless asked.
- Add or update a decision record in the same pull request when it settles a meaningful architecture or product decision.
- Run the documented checks before review. Report what you ran and what you could not run. Never report a check as passing unless you ran it. Do not delete, skip or loosen tests, lint rules or CI to get a green result.
- Ask before destructive actions, major dependency upgrades, or changes to CI or deployment configuration.

## Issue and pull request writing

- Keep the prefix from the issue template in issue titles: `[Task]`, `[Bug]` or `[Epic]`.
- Use a Conventional Commit title for the pull request.
- Fill every section of the [pull request template](.github/PULL_REQUEST_TEMPLATE.md) with the validation actually performed and any outstanding checks.

## Pull request metadata

- Add the applicable existing repository labels.
- Assign the pull request to its author.
- Reference the issue with `Closes #N`, or `Refs #N` for partial work. GitHub closes the issue only when the change reaches `main`; see [CONTRIBUTING](CONTRIBUTING.md#closing-issues).
- Verify the labels, assignee and issue link before reporting the pull request as opened. Say which of them you could not apply.
